`11_tekfusion_policies.sql` (las funciones se pasan a `02_functions.sql` en formato `pg_dump`; las policies `using (true)` de Atomic se **borran** de `05_policies.sql`, no se apilan encima):

```sql
-- Helpers: security definer, stable, search_path vacío; leen la fila del usuario en sales.
create function public.current_sales_id() returns bigint language sql stable security definer
    set search_path = '' as $$ select id from public.sales where user_id = auth.uid() and not disabled $$;
create function public.current_user_role() returns public.user_role language sql stable security definer
    set search_path = '' as $$ select role from public.sales where user_id = auth.uid() and not disabled $$;
create function public.is_manager() returns boolean language sql stable
    set search_path = '' as $$ select coalesce(public.current_user_role() = 'manager', false) $$;
-- Trigger en sales: role/administrator/disabled solo los cambia gerencia; administrator = (role = 'manager').
-- RPC take_deal(deal_id): un ejecutivo toma un lead sin asignar (decisión 4); deja deal_events en Fase 3.

-- deals
create policy deals_select on public.deals for select to authenticated using (
    public.current_user_role() in ('manager', 'reader')
    or sales_id = public.current_sales_id()
    or (sales_id is null and public.current_user_role() = 'executive'));
create policy deals_insert on public.deals for insert to authenticated with check (
    public.is_manager() or (public.current_user_role() = 'executive' and sales_id = public.current_sales_id()));
create policy deals_update on public.deals for update to authenticated
    using (public.is_manager() or sales_id = public.current_sales_id())
    with check (public.is_manager() or sales_id = public.current_sales_id()); -- el ejecutivo no puede reasignar
create policy deals_delete on public.deals for delete to authenticated using (public.is_manager()); -- decisión 3

-- contacts: los ve quien tiene un lead del contacto (o un lead sin asignar), su dueño, gerencia y lector
create policy contacts_select on public.contacts for select to authenticated using (
    public.current_user_role() in ('manager', 'reader')
    or sales_id = public.current_sales_id()
    or exists (select 1 from public.deals d where contacts.id = any (d.contact_ids)));  -- pasa por la RLS de deals
create policy contacts_insert on public.contacts for insert to authenticated
    with check (public.current_user_role() in ('manager', 'executive'));
create policy contacts_update on public.contacts for update to authenticated using (
    public.is_manager() or sales_id = public.current_sales_id()
    or exists (select 1 from public.deals d where contacts.id = any (d.contact_ids)
               and d.sales_id = public.current_sales_id()));
create policy contacts_delete on public.contacts for delete to authenticated using (public.is_manager());

-- companies (decisión 5): lectura interna completa, escritura gerencia/ejecutivo, borrar solo gerencia
create policy companies_select on public.companies for select to authenticated
    using (public.current_user_role() is not null);
create policy companies_write on public.companies for insert to authenticated
    with check (public.current_user_role() in ('manager', 'executive'));
create policy companies_update on public.companies for update to authenticated
    using (public.current_user_role() in ('manager', 'executive'));
create policy companies_delete on public.companies for delete to authenticated using (public.is_manager());

-- deal_notes / contact_notes / tasks heredan la visibilidad del padre vía exists() (misma forma que contacts):
--   select: el padre es visible; insert/update/delete: gerencia o ejecutivo dueño del padre. Lector: solo select.
-- sales: select a todo authenticated; update a la fila propia o gerencia (+ trigger de columnas protegidas).
-- configuration, business_lines, lost_reasons, sales_absences: select authenticated; escritura is_manager().
-- tags: select authenticated; escritura gerencia/ejecutivo.
```

## (d) Decisiones que necesito

1. **Ids `bigint` en vez de `uuid`.** `05` pide `uuid`, pero todas las tablas de Atomic usan `bigint identity` y las nuevas apuntan a ellas. *Recomiendo `bigint`:* claves foráneas homogéneas, cero cambios en el data provider; el `uuid` no aporta seguridad porque la RLS es la que protege, no lo difícil de adivinar un id.
2. **`role` como fuente de verdad, con `administrator` sincronizado.** Alternativa: borrar `administrator` y tocar todos los lugares de Atomic que lo leen (UI de usuarios, `is_admin()`, Edge Function `users`). *Recomiendo sincronizar con trigger:* cambio mínimo y sin riesgo de que una pantalla de Atomic deje de reconocer a gerencia.
3. **Borrado: solo gerencia, no "nadie".** `08` dice que nadie borra leads ni contactos, pero Atomic tiene botones de borrar y `merge_contacts` elimina el contacto duplicado. *Recomiendo permitirlo solo a gerencia:* conserva la fusión de duplicados (que la importación del Sheets va a necesitar) y sigue impidiendo que un ejecutivo borre.
4. **Ejecutivo puede "tomar" un lead sin asignar** (RPC `take_deal`, queda registrado y avisa a gerencia), o solo gerencia asigna. *Recomiendo permitirlo:* `08` ya lo contempla y evita que un lead espere a que gerencia esté disponible; el registro deja trazabilidad.
5. **Empresas visibles para todo usuario interno.** `08` no dice nada de `companies`. *Recomiendo lectura completa:* el autocompletado y la detección de duplicados necesitan ver empresas existentes, y una empresa (razón social, RUT, sector) es dato comercial, no personal; los datos personales están en `contacts`, que sí queda restringido.
